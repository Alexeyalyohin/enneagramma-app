# Эннеаграмма.one

## Обзор
Экосистема вокруг Эннеаграммы: адаптивный тест на сайте ловит анонимный трафик в лид, бесплатный видеоурок продаёт клуб-подписку (закрытый Telegram), B2B-аудитория собирается в лист ожидания сертификации с депозитом. MVP-скоуп: тест → лид → клуб → лист ожидания. Плеер полного курса — вне скоупа.

## Стек технологий
- Frontend: Next.js 16 (App Router), TypeScript 5.x, Tailwind CSS v4, shadcn/ui
- Backend: Supabase (PostgreSQL 15, Auth — только для владельца, RLS, Storage)
- Деплой: Vercel (фронт + API Routes + Vercel Cron)
- Платежи: Prodamus — подключён к **Salebot** (рекуррент клуба). Приложение зовёт Prodamus напрямую только для разового депозита листа ожидания.
- Telegram: бот на **Salebot** (внешний конструктор) — приложение не владеет токеном бота
- Сайт: существующая Tilda (`enneagramma.one`); тест встраивается iframe с `test.enneagramma.one`

## Архитектура
Три слоя с чёткой границей ответственности:
- **Tilda** — маркетинг, лендинги, оффер клуба. Не трогаем.
- **Приложение (это репо)** — адаптивный тест, описания типов, админка/метрики, приёмник вебхуков Salebot/Prodamus.
- **Salebot** — весь Telegram-слой: захват подписчиков, оплата/рекуррент клуба (Prodamus), доступ в закрытый канал, кик, рассылки.

**Ключевое решение:** B2C-пользователи НЕ получают Supabase Auth. Лид опознаётся по `telegram_id` или `phone`. Через Supabase Auth аутентифицируется только владелец (`admin`). Клиентские браузеры не обращаются к БД напрямую — вся запись идёт server-side через `service_role`; RLS закрыта для anon/authenticated, открыта на чтение только для `admin`.

**Источник правды:** операционный статус доступа/подписки клуба — Salebot (он реально управляет каналом и рекуррентом). Supabase — аналитическое зеркало + движок теста + контент. Таблицы `club_subscriptions` и `telegram_access_grants` заполняются ТОЛЬКО вебхуками, не бизнес-логикой приложения.

**Жёсткое ограничение:** приложение НЕ вызывает Telegram Bot API, НЕ ведёт чекаут/рекуррент клуба, НЕ кикает из канала. Всё это — Salebot↔Prodamus. Нарушение этого правила — архитектурная ошибка, а не деталь реализации.

Полная спецификация (роуты, data model, API, UI/UX, business logic, edge cases) — в `Чертёж.md`.

## Правила кодирования
- TypeScript strict mode, без `any`
- Именование: camelCase для переменных, PascalCase для компонентов, snake_case + множественное число для таблиц БД
- Компоненты: один компонент = один файл, максимум 200 строк
- Импорты: абсолютные через `@/` алиас
- Суммы — всегда `INTEGER` в копейках, отображение с форматированием (`1 490 ₽`)
- Телефон — нормализация в E.164 (`+7XXXXXXXXXX`) до записи в БД
- Часовой пояс расчётов и кронов — `Europe/Moscow` (MSK)
- Обработка ошибок: try/catch для async, Error Boundaries для компонентов

## Работа с Supabase
- Все изменения схемы — через миграции в `supabase/migrations/`
- RLS обязательна для каждой таблицы: anon/authenticated без политик записи, `admin` — SELECT через `is_admin()`, запись — `service_role` в серверных роутах
- Типы генерировать через: `npx supabase gen types typescript --project-id $PROJECT_REF > src/types/database.ts`

## Context7
При работе с любыми внешними библиотеками (Next.js, React, Supabase, Tailwind и т.д.) ВСЕГДА используй Context7 MCP для получения актуальной документации перед написанием кода. Добавляй "use context7" к запросам, связанным с API библиотек.
