# Эннеаграмма.one — Техническая спецификация (Чертёж)

> Версия: 1.0 | Дата: 2026-08-06 | Статус: Production-ready
> Скоуп: MVP-воронка (тест → лид → клуб → лист ожидания сертификации). Плеер полного курса — вне этого Чертежа.

---

## 0. Обзор проекта

### Что это
Экосистема вокруг Эннеаграммы: адаптивный тест на сайте ловит анонимный трафик в **лид** (телефон/telegram), бесплатный видеоурок продаёт **клуб-подписку** (закрытый Telegram, приём оплаты через Prodamus), а B2B-аудитория собирается в **лист ожидания сертификации** с депозитом. Приложение управляет воронкой, платежами, выдачей/отзывом доступа в Telegram и даёт владельцу единую админку с метриками конверсии.

### Ключевое архитектурное решение
**B2C-пользователи НЕ получают аккаунт Supabase Auth в MVP.** Лид опознаётся по `telegram_id` ИЛИ номеру телефона. Доступ к клубу выдаёт **бот на Salebot** (не приложение напрямую). Через Supabase Auth аутентифицируется **только владелец** (роль `admin`). Следствие: клиентские браузеры не обращаются к БД напрямую — вся запись идёт server-side через `service_role` внутри валидированных API-роутов; RLS работает как «глухая стена» для anon/authenticated и открывается только для `admin` на чтение.

### Топология интеграции: Tilda + приложение + Salebot
Три слоя с чёткой границей ответственности — приложение **не переписывает** сайт и **не дублирует** бота:
- **Tilda (`enneagramma.one`, как есть):** маркетинг, лендинги, страница-оффер клуба с видеоуроком. Ничего не сносим. Тест и результат **встраиваются в Tilda** (iframe с сабдомена `test.enneagramma.one`, где крутится Next.js; либо HTML-блок Tilda). Кнопки «пройти тест»/«вступить в клуб» на Tilda ведут в приложение и в бота.
- **Приложение (Next.js на Vercel + Supabase):** только то, чего Tilda и Salebot не умеют — **адаптивный тест** (движок), **описания типов**, **админка/метрики**, приёмник вебхуков от Salebot. Приложение **НЕ** дёргает Telegram Bot API и **НЕ** ведёт клубную подписку операционно.
- **Salebot (существующий бот, перерабатывается):** весь Telegram-слой воронки клуба — захват в подписчики, приём оплаты **Prodamus (нативно, рекуррент)**, автодобавление в закрытый канал, автокик при неоплате, жизненный цикл подписки, пробный доступ, сегменты, рассылки-дожимы.

**Поток данных:**
1. Тест (приложение, во фрейме Tilda) → результат + тип. CTA «получать разборы / вступить в клуб» → deep-link в Salebot-бота: `https://t.me/<bot>?start=<token>`, где `token` кодирует `session_id` (и тип).
2. Salebot по `start`-токену опознаёт подписчика, дёргает `POST /api/leads/link-telegram` (или тянет тип из приложения по API) → в приложении `telegram_id` привязывается к лиду, тип пишется в переменную подписчика Salebot.
3. Оплата/доступ/рекуррент/кик — **целиком в Salebot** (Prodamus↔Salebot). На каждое событие (подписался, оплатил, продлил, отвалился, кикнут) Salebot шлёт `POST /api/webhooks/salebot` → приложение пишет зеркало в `events`/`leads`/`club_subscriptions` **для метрик**.
4. **Источник правды:** операционный статус доступа/подписки — Salebot (он реально управляет каналом); Supabase — аналитическое зеркало + движок теста + контент.

### Стек
- **Frontend:** Next.js 16 (App Router), TypeScript 5.x, Tailwind CSS v4, shadcn/ui
- **Backend:** Supabase (PostgreSQL 15, Auth — только для владельца, RLS, Storage)
- **Деплой:** Vercel (фронт + API Routes + Vercel Cron)
- **Платежи:** Prodamus — подключён **к Salebot** (клуб: рекуррент/автосписания). Приложение напрямую Prodamus не ведёт (исключение — опц. депозит листа ожидания, см. форк ниже). Абстракция `PaymentProvider` в приложении сохранена на случай app-direct платежей.
- **Telegram:** бот на **Salebot** (конструктор) — приём оплаты, доступ в закрытый канал, жизненный цикл подписки, рассылки. Приложение не владеет токеном бота и не вызывает Telegram Bot API; общается с Salebot по его API/вебхукам.
- **Сайт/встраивание:** существующая **Tilda** (`enneagramma.one`) остаётся; тест приложения встраивается в Tilda (iframe с сабдомена `test.enneagramma.one` или HTML-блок)
- **Валюта:** все суммы хранятся в `INTEGER` (копейки), отображаются с форматированием (`1 490 ₽`)
- **Часовой пояс расчётов:** `Europe/Moscow` (MSK) — фиксирован для дедлайнов и крон-задач

## БЛОК 1: User Stories

### US-001: Прохождение адаптивного теста
**Как** человек 14–45 лет, зашедший на сайт ради теста,
**я хочу** пройти короткий адаптивный тест и точно узнать свой тип,
**чтобы** понять, как я устроен, без «гороскопной» воды.

**Сценарий:**
1. Лид открывает `/test` (переход с Tilda или из Telegram).
2. Система создаёт `test_session` (`status='in_progress'`), кладёт `session_id` в URL и localStorage.
3. Лид проходит 12 форсированных триад на сетке 3×3 (социальная ось × гармоническая ось); каждый ответ уходит `POST /api/test/answer` и сохраняется в `answers` сессии.
4. После триад система показывает 3-вопросный чек центра (тело/сердце/голова) как кросс-валидацию.
5. Если топ-ячейка и раннер-ап различаются меньше порога — система задаёт адаптивные tiebreak-вопросы по конкретной паре типов (из 19 спорных пар).
6. Лид жмёт «Показать результат» → `POST /api/test/submit`.
7. Система считает тип, крыло, уверенность, помечает `status='completed'`, редиректит на `/test/result/[sessionId]`.

**Критерии приёмки:**
- [ ] Тест проходится за ≤ 4 минут (12 триад + 3 центра + до 4 tiebreak).
- [ ] Кнопка «Назад» возвращает к предыдущему вопросу без потери ответов.
- [ ] Обновление страницы (F5) восстанавливает сессию из БД по `session_id`.
- [ ] Порядок вариантов в триаде перемешивается (нет позиционного смещения).
- [ ] Живая визуализация матрицы 3×3 обновляется после каждого ответа.
- [ ] Незавершённая сессия старше 24 ч не показывает результат — предлагает начать заново.

### US-002: Захват лида и подписка на бесплатный Telegram
**Как** человек, увидевший точное описание своего типа,
**я хочу** сохранить результат и подписаться на бесплатный Telegram,
**чтобы** получить больше и не потерять свой тип.

**Сценарий:**
1. На `/test/result/[sessionId]` лид читает портрет типа от первого лица.
2. Под портретом — блок «Сохранить результат и получать разборы»: поле телефона **или** кнопка «Подписаться через Telegram» (в боте телефон удобно собрать через кнопку «Поделиться контактом»).
3. Лид отмечает чекбокс согласия 152-ФЗ (обязательно), вводит телефон → `POST /api/leads/capture`.
4. Система создаёт/находит `lead`, привязывает `test_session` к `lead_id`, пишет `enneagram_type` в лид.
5. Показывается CTA-кнопка «Открыть Telegram-канал» (deep-link `https://t.me/enneagramma_one`).
6. Событие `lead_captured` пишется в `events` для метрик воронки.

**Критерии приёмки:**
- [ ] Без чекбокса согласия кнопка отправки неактивна.
- [ ] Дубликат телефона/telegram не создаёт второй лид — обновляет существующий (мердж).
- [ ] Телефон нормализуется в E.164 (`+7XXXXXXXXXX`; ведущая `8`→`7`) и валидируется до отправки.
- [ ] После захвата результат доступен по прямой ссылке навсегда (не привязан к сессии браузера).
- [ ] CTA в Telegram — единственное следующее действие (нет платного трипваера).

### US-003: Видеоурок и вступление в клуб (через бота Salebot)
**Как** тёплый подписчик,
**я хочу** посмотреть бесплатный видеоурок и вступить в клуб по цене основателя,
**чтобы** учиться Эннеаграмме регулярно за понятную цену.

**Сценарий:**
1. Лид видит оффер клуба (видеоурок + `1 490 ₽/мес`, цена основателя) — **страница на Tilda** или экран/сообщение в боте.
2. Жмёт «Вступить в клуб» → попадает в **бота Salebot** (deep-link, если пришёл с сайта/из результата теста).
3. Приём оплаты, цена основателя, рекуррент, автодоступ в закрытый канал — **целиком Salebot ↔ Prodamus** (нативная интеграция, автосписания).
4. На событие «оплатил» Salebot шлёт `POST /api/webhooks/salebot` → приложение зеркалит `club_subscriptions(status='active', is_founder_price, price_kopecks, current_period_end)` + событие `club_paid` в `events` (для метрик).

**Критерии приёмки:**
- [ ] Цена основателя настроена как товар-подписка в Prodamus/Salebot; после точки Х оффер переключается на `2 190 ₽` (для новых). Зеркало пишет `price_kopecks`/`is_founder_price` из вебхука Salebot.
- [ ] Приложение **не** держит `PRODAMUS_SUBSCRIPTION_ID` и не собирает payform само — этим владеет Salebot.
- [ ] Повторная доставка вебхука об одной оплате не создаёт вторую подписку (идемпотентность по `provider_payment_id`/`salebot_event_id`).

### US-004: Доступ в закрытый Telegram (выдаёт Salebot)
**Как** оплативший клуб,
**я хочу** автоматически попасть в закрытый канал,
**чтобы** не ждать ручной выдачи доступа.

**Сценарий:**
1. Доступ в закрытый канал выдаёт **Salebot** сразу после подтверждённой оплаты (нативная функция клуба: автодобавление в канал/чат).
2. Salebot уведомляет приложение (`POST /api/webhooks/salebot`, событие `access_granted`) → зеркалим `telegram_access_grants(status='granted', granted_at)` для метрик.

**Критерии приёмки:**
- [ ] Приложение **не** вызывает `createChatInviteLink`/Telegram Bot API — доступ выдаёт Salebot.
- [ ] Если событие доступа не пришло за N минут после `club_paid` — крон `retry-salebot-sync` подсвечивает рассинхрон в админке (без вмешательства в сам доступ, которым управляет Salebot).

### US-005: Продление и истечение подписки клуба (владеет Salebot)
**Как** владелец,
**я хочу**, чтобы продление, неоплата и кик из канала работали автоматически,
**чтобы** платящие оставались, а неплатящие теряли доступ — **без логики на стороне приложения**.

**Сценарий:**
1. Рекуррент, ретраи списания и **автокик при неоплате** выполняет **Salebot ↔ Prodamus** (настройки числа попыток/интервала — в ЛК).
2. На каждое событие (`renewed`, `past_due`, `churned`/`kicked`) Salebot шлёт `POST /api/webhooks/salebot` → приложение обновляет зеркало `club_subscriptions.status` и пишет событие в `events`.
3. Приложение **не** списывает деньги, **не** кикает из канала, **не** держит крон-жизненный цикл подписки — только зеркалит статусы для дашборда.

**Критерии приёмки:**
- [ ] В приложении нет `renew`/`revoke`-кронов и вызовов Telegram Bot API — весь операционный цикл в Salebot.
- [ ] Зеркало подписки идемпотентно: повторный вебхук не двоит период и не плодит события.
- [ ] Кик из канала (в Salebot) не удаляет лида из БД приложения (история/метрики сохраняются).

### US-006: Лист ожидания сертификации с депозитом
**Как** психолог/коуч (B2B),
**я хочу** записаться в лист ожидания флагмана и внести депозит,
**чтобы** зафиксировать место и раннюю цену до старта продаж.

**Сценарий:**
1. Лид открывает `/waitlist`, выбирает интересующий тариф (самостоятельный / с сопровождением / практик+сертификат).
2. Оставляет контакт + согласие 152-ФЗ → `POST /api/waitlist`.
3. Опционально жмёт «Внести депозит» → `POST /api/waitlist/deposit` → ЮKassa (разовый платёж).
4. Вебхук подтверждает → `waitlist_entry.deposit_status='paid'`, `payment` со `product_type='deposit'`.
5. Событие `waitlist_deposit_paid`.

**Критерии приёмки:**
- [ ] Депозит опционален — можно просто встать в лист.
- [ ] Сумма депозита — env `DEPOSIT_AMOUNT_KOPECKS` (дефолт `500000` = 5 000 ₽).
- [ ] Депозит фиксирует тариф-интерес; смена тарифа возможна до старта продаж.
- [ ] Метрика «≥5 оплаченных депозитов» видна в админке (порог валидации флагмана).

### US-007: Дашборд воронки для владельца
**Как** владелец,
**я хочу** видеть конверсию по шагам воронки и список лидов,
**чтобы** понимать, где утечка, и когда собирать флагман.

**Сценарий:**
1. Владелец логинится на `/auth/login`, попадает на `/admin`.
2. Дашборд показывает воронку: визиты теста → завершённые тесты → захваченные лиды → подписки Telegram → активные клубы → депозиты.
3. Каждый шаг — абсолют + конверсия из предыдущего.
4. Владелец кликает шаг → `/admin/leads` с фильтром по стадии.

**Критерии приёмки:**
- [ ] Метрика «сайт → подписчик» выделена как главная (узкое горлышко).
- [ ] Данные считаются из `events` за выбранный период (7/30/90 дней).
- [ ] MRR клуба = сумма `price_kopecks` активных подписок.
- [ ] Пустой период показывает Empty-состояние, не ошибку.

### US-008: Аутентификация владельца
**Как** владелец,
**я хочу** входить по email и паролю,
**чтобы** только я имел доступ к админке.

**Сценарий:**
1. `/auth/login` — форма email+пароль (Supabase Auth).
2. Успех → сессия, редирект на `/admin`.
3. Middleware проверяет `is_admin()` на всех `/admin/*` и `/api/admin/*`.
4. Не-админ на `/admin/*` → редирект на `/auth/login`.

**Критерии приёмки:**
- [ ] Регистрация закрыта — единственный admin создаётся вручную в Supabase, публичного sign-up нет.
- [ ] Неверный пароль → «Неверный email или пароль» (без утечки, какое поле неверно).
- [ ] Сессия истекает через 7 дней бездействия.
- [ ] Прямой заход не-админа на `/api/admin/*` → 403.

## БЛОК 2: Data Model

### Диаграмма связей
```
auth.users        1──1 profiles (id)                    -- только владелец
leads             1──N test_sessions   (lead_id, NULL до захвата)
leads             1──N club_subscriptions (lead_id)
leads             1──N waitlist_entries (lead_id)
leads             1──N payments        (lead_id)
leads             1──N telegram_access_grants (lead_id)
leads             1──N events          (lead_id, NULL для анонимных)
type_descriptions 1──N leads           (enneagram_type → type, логическая связь)
club_subscriptions 1──N payments       (subscription_id, NULL для депозитов)
```

### Общие объекты (выполнить первыми)
```sql
CREATE EXTENSION IF NOT EXISTS moddatetime;

-- Проверка, что текущий пользователь — владелец
CREATE OR REPLACE FUNCTION is_admin() RETURNS BOOLEAN AS $$
  SELECT EXISTS (
    SELECT 1 FROM profiles
    WHERE profiles.id = auth.uid() AND profiles.role = 'admin'
  );
$$ LANGUAGE sql SECURITY DEFINER STABLE;

-- Пояснение по RLS во всех таблицах ниже:
-- anon / authenticated НЕ имеют политик записи → доступ закрыт.
-- Запись выполняет service_role (серверные API-роуты), который обходит RLS.
-- admin получает SELECT через is_admin() для чтения в админке.
```

### profiles (только владелец)
```sql
CREATE TABLE profiles (
  id UUID PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  full_name TEXT NOT NULL DEFAULT 'Владелец',
  role TEXT NOT NULL DEFAULT 'admin' CHECK (role IN ('admin')),
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);
```

## БЛОК 3: API Endpoints

**Общие правила:**
- Публичные роуты не требуют auth, но защищены rate-limit (см. Блок 5) и валидацией Zod.
- Ошибки: `{ "error": { "code": "ERROR_CODE", "message": "..." } }`.
- Пагинация: `{ "data": [...], "meta": { "total": N, "page": P, "per_page": PP } }`.
- Запись — через Supabase `service_role` client (server-only).

### GROUP: Клуб (хендофф в Salebot)

> Оплата, подписка, доступ в канал и рекуррент клуба — **в Salebot**, не в приложении. У приложения нет `checkout`-эндпоинта с payform. Оно лишь передаёт лида в бота и принимает вебхуки статусов (ниже).

#### `POST /api/club/start`
**Описание:** Отдать deep-link в бота Salebot с токеном сессии/лида (клик «Вступить в клуб»). **Авторизация:** Публичный.

**Запрос:**
```json
{ "session_id": "3f1c...", "phone": "+79990001122", "consent_152fz": true }
```
**Ответ 200:**
```json
{ "data": { "bot_deep_link": "https://t.me/<bot>?start=club_<signed_token>" } }
```
> `signed_token` кодирует `lead_id`/`session_id` (HMAC, TTL). Salebot по нему опознаёт подписчика и запускает клубный сценарий (оплата Prodamus → доступ). `consent_152fz` фиксируется на стороне приложения до выдачи ссылки.

**Zod:** `z.object({ session_id: z.string().uuid().optional(), phone: z.string().transform(normalizePhoneE164).refine(v => /^\+7\d{10}$/.test(v)).optional(), consent_152fz: z.literal(true) }).refine(d => d.phone || d.session_id)`

**Описание:** Salebot связывает `telegram_id` подписчика с лидом по `start`-токену и (опц.) отдаёт тип из теста. **Авторизация:** секрет Salebot в заголовке/URL.

> Приложение проверяет подпись токена, привязывает `telegram_id` к лиду (мердж при конфликте), возвращает тип — Salebot кладёт его в переменную подписчика для сегментации/рассылок.

> Депозит — разовый платёж (без блока `subscription`): подписанная ссылка на payform с суммой/товаром, `order_id` = локальный `payment_id`, `urlNotification` → вебхук.

### GROUP: Вебхуки

#### `POST /api/webhooks/prodamus`
**Описание:** Приём уведомлений Prodamus **только по разовому депозиту листа ожидания** (B2B, без Telegram-канала). Клубную подписку/рекуррент ведёт Salebot — сюда они не приходят. **Авторизация:** HMAC-SHA256 по `PRODAMUS_SECRET_KEY`.

**Формат:** тело `multipart/form-data` (НЕ JSON). Подпись — в заголовке (`Sign`) или поле `signature`. Проверка: значения→строки → сортировка ключей по алфавиту (вглубь) → JSON → sha256 секретным ключом → сравнить (класс `Hmac.verify`).

**Разовый платёж (депозит) — пример полей:**
```
order_id=d7c6...   sum=5000.00   currency=rub   payment_status=success
customer_phone=+79990001122   customer_email=psy@mail.ru   date=2026-08-06T21:00:00+03:00   signature=<hmac>
```
Обработка: `order_id` → локальный `payment_id` депозита → `status='succeeded'`, `waitlist_entry.deposit_payment_id` проставляется, событие `waitlist_deposit_paid`.

**Ответ 200:** `{ "ok": true }` (обязателен при успешной обработке — иначе Prodamus ретраит доставку).
**Ответ 400:** `{ "error": { "code": "INVALID_SIGNATURE", "message": "Не удалось верифицировать подпись" } }`

#### `POST /api/webhooks/salebot`
**Описание:** Приём событий бота Salebot (оплата клуба, доступ, продление, отвал, кик) для зеркала метрик. **Авторизация:** секрет Salebot в URL/заголовке (+ опц. HMAC).

**Запрос (пример):**
```json
{ "event": "club_paid", "salebot_event_id": "evt_88f...",
  "lead": { "telegram_id": 123456789, "phone": "+79990001122" },
  "subscription": { "provider_payment_id": "prod_9a...", "amount_kopecks": 149000,
    "is_founder_price": true, "current_period_end": "2026-09-06T00:00:00+03:00" } }
```

## БЛОК 5: Business Logic

### Алгоритм определения типа (v0.4)

**Сетка 3×3: социальная ось × гармоническая ось.** Каждая ячейка = уникальный тип (каноническая структура Эннеаграммы):

| | Позитивный настрой | Компетентность | Реактивность |
|---|---|---|---|
| **Ассертивные** (против) | 7 | 3 | 8 |
| **Долженствующие** (к) | 2 | 1 | 6 |
| **Отстранённые** (от) | 9 | 5 | 4 |

**Шаги расчёта:**
1. **12 триад.** Каждая триада даёт +1 либо социальной категории (assertive/compliant/withdrawn), либо гармонической (positive/competency/reactive) — половина триад грузит одну ось, половина другую (по 6 на ось). Итог: `social = argmax(social_scores)`, `harmonic = argmax(harmonic_scores)` → ячейка = кандидат-тип.
2. **Чек центра (3 вопроса).** Считает доминантный центр (gut: 8/9/1, heart: 2/3/4, head: 5/6/7). Если центр кандидат-типа совпадает с чеком — уверенность растёт; если нет — понижается и возможен tiebreak.
3. **Confidence.** `confidence = clamp( 0.5 + 0.5 * (margin_social + margin_harmonic)/12 + center_bonus, 0, 1)`, где `margin_*` = разрыв между лидером оси и раннер-апом (в баллах), `center_bonus = +0.1` при совпадении центра, `-0.15` при конфликте.
4. **Tiebreak (адаптивно).** Если `confidence < 0.7` ИЛИ разрыв по любой оси = 0 — система выбирает спорную **пару типов** и задаёт 1–2 форсированных вопроса из набора `tiebreak_items`. Пар — 19 (соседи по кругу, крылья и «двойники»): например `4_5`, `6_9`, `2_3`, `1_8`, `3_7`, `9_1`, `4_6`, `5_9`, `2_6`, `7_9` и т.д. Каждая пара — 2 различающих вопроса.
5. **Крыло.** Определяется по второму по силе соседу кандидат-типа на круге: из двух соседей берётся тот, чьи оси ближе к вторичным баллам. `wing ∈ {type-1, type+1}` по кругу Эннеаграммы.
6. **Итог** пишется в `test_sessions.result` и (при захвате) в `leads.enneagram_type/wing`.

**Что при нарушении:** если ответов меньше минимума (15) — `422 INSUFFICIENT_ANSWERS`, результат не считается. Если после tiebreak уверенность всё ещё < 0.6 — тип показывается, но с честной пометкой «пограничный между N и M» (не скрываем неопределённость — это часть научной честности бренда).

### Разрешение идентичности лида (дедуп/мердж)
- Ключи идентичности: нормализованный `phone` (E.164) и `telegram_id`. `email` — вторичное поле, в дедупе не участвует.
- При `capture`/`checkout`: ищем лид по любому из ключей.
  - Найден один → обновляем недостающие поля.
  - Найдены два разных (телефон в одном лиде, telegram в другом) → **мердж** в старший (по `created_at`): переносим FK (`test_sessions`, `payments`, ...) на старший, второй помечаем удалённым через архивную запись, возвращаем `merged: true`.
  - Не найден → создаём новый.
- Правило: `enneagram_type` перезаписывается только если был `NULL` или пришёл более уверенный результат (`confidence` выше).

### Жизненный цикл подписки клуба (владеет Salebot, приложение зеркалит)
> Оплату, рекуррент (Prodamus), доступ в канал и кик ведёт **Salebot**. Приложение хранит `club_subscriptions` как **аналитическое зеркало**, обновляемое вебхуками `/api/webhooks/salebot`. Никаких списаний, инвайтов и киков в приложении.
- **Создание:** событие `club_paid` → зеркало `active`, `price_kopecks`/`is_founder_price`/`current_period_end` из полей вебхука.
- **Цена основателя:** реализуется как отдельный товар-подписка (или промо) в Prodamus/Salebot; после точки Х оффер переключается на `2 190 ₽` для новых. Существующим цена не меняется (свойство подписки Prodamus). Приложение лишь фиксирует, что пришло.
- **Продление:** событие `subscription_renewed` → двигаем `current_period_end` в зеркале. Идемпотентно по `salebot_event_id`.
- **Past due / отвал:** события `subscription_past_due` / `subscription_churned` → соответствующий `status` в зеркале.
- **Кик:** событие `access_revoked` → `telegram_access_grants.status='revoked'` в зеркале. Сам кик делает Salebot.

### Доступ в закрытый Telegram (владеет Salebot)
- **Grant/Revoke:** выполняет Salebot нативно (автодобавление в канал при оплате, автокик при неоплате). Приложение только зеркалит `telegram_access_grants` по вебхукам `access_granted`/`access_revoked` — для метрик.
- **Линковка `telegram_id`:** лид жмёт CTA → deep-link `https://t.me/<bot>?start=club_<token>`; Salebot вызывает `POST /api/leads/link-telegram` с `telegram_id` и токеном → приложение привязывает лид и отдаёт тип. Приложение **не** держит токен бота и **не** принимает Telegram-апдейты напрямую.

### Интеграция: Prodamus — только разовый депозит (за абстракцией `PaymentProvider`)
> **Клубный рекуррент Prodamus ведёт Salebot, не приложение.** Приложение обращается к Prodamus напрямую **только** для разового депозита листа ожидания (B2B, без Telegram-канала). Если депозит тоже решишь вести через бота — этот раздел выключается целиком (см. форк в конце).
> **Важно (вне скоупа Чертежа):** мерчант и юрлицо решаются с юристом по банкротству ДО выручки (см. Идея, блок 5). Ключи — через env: `PRODAMUS_FORM_URL` (поддомен payform), `PRODAMUS_SECRET_KEY`, `PRODAMUS_SYS`. Абстракция `PaymentProvider` сохранена (адаптер ЮKassa подключается сменой env).

**Предусловие в ЛК Prodamus (ручная настройка, не код):** страница оплаты для депозита, `urlNotification` → `/api/webhooks/prodamus`, секретный ключ.

Интерфейс (урезан до разовых платежей — подписки не здесь):
```ts
interface PaymentProvider {
  // Разовый платёж (депозит): собирает подписанную ссылку на payform
  createPayment(p: { amountKopecks: number; description: string;
    orderId: string; customerPhone: string; customerEmail?: string;
    metadata: Record<string,string> }): Promise<{ confirmationUrl: string }>;
  // Проверка подписи входящего вебхука (Prodamus: HMAC-SHA256 через класс Hmac)
  verifyWebhook(headers: Record<string,string>, rawBody: string): boolean;
}
```
- **Что отправляем:** подписанную ссылку на payform (`order_id`, товар/сумма депозита, `customer_phone`, опц. `customer_email`, `urlSuccess`, `urlNotification`, `signature`). Суммы — из `INTEGER` копеек в рубли с копейками.
- **Что получаем:** подтверждение — ТОЛЬКО подписанный вебхук (`multipart/form-data`) на `urlNotification`; возврат на `urlSuccess` доверием не считается.
- **Верификация:** HMAC-SHA256 по `PRODAMUS_SECRET_KEY`. Не совпало → `400 INVALID_SIGNATURE`.
- **Идемпотентность:** `idempotence_key` (UUID) и `(provider, provider_payment_id)` уникальны в `payments`.
- **Retry:** отдельного API опроса статуса нет — Prodamus сам ретраит доставку до `200`.

### Интеграция: Salebot (Telegram-слой воронки клуба)
> Существующий бот **перерабатывается**, не заменяется. Salebot владеет токеном бота, приёмом Prodamus (рекуррент), доступом в закрытый канал, жизненным циклом подписки, пробным доступом, сегментами и рассылками.
- **Приложение → Salebot:** deep-link `?start=club_<token>` (передача лида в бота); при желании — вызовы Salebot API, чтобы записать переменную подписчика (тип из теста) или запустить блок сценария.
- **Salebot → приложение:** `POST /api/leads/link-telegram` (связать `telegram_id` с лидом, забрать тип) и `POST /api/webhooks/salebot` (события оплаты/доступа/рекуррента/кика для зеркала метрик).
- **Аутентификация:** секрет Salebot в URL/заголовке вебхука (+ опц. HMAC). Идемпотентность входящих событий — по `salebot_event_id`.
- **Обработка ошибок:** приложение всегда отвечает `200` при принятии валидного события; при рассинхроне (нет `access_granted` после `club_paid`) — подсветка в админке кроном `retry-salebot-sync`. Сообщения, инвайты, кики — ответственность Salebot, приложение их не шлёт.

### Безопасность
- **Аутентификация:** Supabase Auth (email+пароль) только для владельца; публичного sign-up нет. Middleware проверяет `is_admin()` на `/admin/*` и `/api/admin/*`.
- **Авторизация:** RLS — все таблицы закрыты для anon/authenticated, чтение открыто только `admin`; запись — `service_role` в API-роутах.
- **Валидация:** Zod на каждом POST-роуте до обращения к БД.
- **Rate limiting (per IP):** `/api/test/*` — 60/мин; `/api/leads/capture` и `/api/leads/link-telegram` — 10/мин; `/api/club/start` и `/api/waitlist/deposit` — 5/мин; вебхуки — без общего лимита, но каждый проверяется по подписи (HMAC/секрет).
- **Санитизация:** `portrait_md` и любой пользовательский текст рендерятся через безопасный Markdown-рендер без сырого HTML.
- **ПДн (152-ФЗ):** согласие фиксируется (`consent_152fz`, `consent_at`); ПДн (телефон/email/telegram) не пишутся в URL/query; страница `/legal/consent` доступна публично; уведомление РКН — организационная задача владельца, вне кода.

## БЛОК 6: Edge Cases

### Сеть и доступность
| # | Ситуация | Триггер | Поведение системы |
|---|----------|---------|-------------------|
| 1 | Пропала сеть при ответе в тесте | `POST /api/test/answer` не дошёл | Ответ буферизуется локально, retry при восстановлении; UI не блокируется |
| 2 | API вернул 500 при submit | `POST /api/test/submit` | `Toast` + retry через 3 с, до 3 попыток |
